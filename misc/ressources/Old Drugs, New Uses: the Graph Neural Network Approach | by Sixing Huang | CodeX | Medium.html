Old Drugs, New Uses: the Graph Neural Network Approach

Using PyG’s link prediction to find new drug indications

Sixing Huang
13 min read
·
May 8, 2024

--

The road to a new drug is long and costly. According to the National Institutes of Health, it takes a decade and over $1 billion to shepherd a potential drug from initial discovery to final approval. And more than 95% of drugs failed during this process (1). Even more concerning is Eroom’s Law (a play on Moore’s Law but spelled backward), which predicts a future where drug development becomes even more expensive and time-consuming, despite all the advancements in high-throughput screening, biotechnology, and computational tools (1, 2). Simply discovering new chemicals won’t be enough to reverse this trend. Repurposing existing drugs for new uses presents a promising alternative, and a specific type of artificial intelligence called graph neural network (GNN) can be a powerful tool for scientists in this endeavor.

GNN belongs to graph machine learning (GML), and GML is in turn a subfield of machine learning. As its name suggests, GML operates on graph data. Graphs use nodes to represent individual entities and connect these nodes with edges (Figure 1). Compared to tabular machine learning, graph machine learning can add extra information to nodes by aggregating data from their neighbors. GML can be used either to predict node properties (read my previous example here) or to recommend new connections that might exist. And drug repurposing is a good use case of the latter. Here, drugs and diseases become nodes, and existing indications act as the links between them. GML can then identify promising new connections, suggesting potential uses for existing drugs (Figure 1).

However, books and tutorials about GML and GNN are scarce. The graph platform Neo4j offers GML within its Graph Data Science library (GDS). However, it is restricted to graphs stored in Neo4j. For broader use, libraries like PyTorch Geometric (PyG) and Deep Graph Library (DGL) are better options. Following the book ‘Graph Neural Networks in Action,’ I experimented with drug repurposing using PyG’s GraphSAGE algorithm, achieving an ROC AUC score of 88%. This article dives into this project using GNNs. Scripts for data engineering are available on my GitHub repository here.

1. Architecture and data

Figure 1 summarizes the core concept of the project. We built a graph with two types of nodes: diseases and drugs. Drugs were linked to their known diseases through “MAY_BE_TREATED_BY” relationships. This graph was then used to train a GraphSAGE GNN model. The trained model predicted potential new treatment applications (indications) for existing drugs. Finally, I reviewed the literature for evidence supporting the high-scoring predictions. The details are as follows.

The disease list contains 410 names. Through the NIH’s Unified Medical Language System (UMLS) API, I first collected their hierarchical categories (Figure 2, right panel). Furthermore, I retrieved their lists of drugs under the “may_be_treated_by” relationship (Figure 2, left).

This first round of API calls resulted in 2,945 drugs. Again through the UMLS API, I got their mechanisms of action (MOA), parents, and physiologic effect (PE).

I then loaded these data into Neo4j for some preliminary analysis (Figure 4).

The graph structure in Figure 4 isn’t suitable for PyG’s link prediction task on mixed-type graphs (heterogeneous graphs). PyG requires bipartite graphs, which have two node types connected by a single relationship type. To achieve this, we eliminated the “BELONGS_TO” relation (Figure 4) by incorporating disease categories as properties of the disease nodes themselves. These “category” properties can then be used as one-hot features within the GNN model. A simple strategy is just to take the values of a certain level on the hierarchy. For example, if we select the fifth level, “Otorhinolaryngologic Diseases”, “Respiratory Tract Diseases”, and “Infections” would become the values in the “category” property of sinusitis (Figure 2).

I calculated the number of categories on each level and found that the fifth level strikes a good balance. On the one hand, there are 24 different categories on that level after a cleanup. That is not too many for a one-hot feature. On the other hand, those categories remain understandable for general audiences. In comparison, drugs had MOA, parents, and PE as node properties. The pipe symbol “|” was used to separate multiple property values.

Figure 5 shows the bipartite graph after the feature conversion. It contains 2,945 drugs, 410 diseases, and 6,692 drug-disease pairs (Figure 5). They were stored as three separate TSV files. Figure 6 is a snapshot of the disease TSV file.

2. PyG

I then turned to PyG to implement a Graph Neural Network (GNN) model. PyG is a Python library for graph neural networks. You can run this whole PyG project on a GPU in Google Colab. I uploaded the three TSV files to Google Drive and then exposed them to Colab via the Mount Drive button. In Code 1, I loaded the files in pandas data frames.

## Code 1
drug_path = '/content/drive/MyDrive/drug_link_prediction/drug.tsv'
disease_path = '/content/drive/MyDrive/drug_link_prediction/disease_category.tsv'
disease_drug_path = '/content/drive/MyDrive/drug_link_prediction/disease_drug.tsv'

drug_df = pd.read_csv(drug_path, index_col='RXNORM_id', sep="\t")

disease_df = pd.read_csv(disease_path, index_col='id', sep="\t")

treatment_df = pd.read_csv(disease_drug_path, sep="\t")

While real-world graphs come in many shapes and sizes, they all can be handled by PyG when transformed into clean, pure mathematical matrices. To get the data into PyG formats, I one-hot encoded the node features and also assigned new numerical identifiers (re-indexed) to each node. Finally, I rebuilt the edges based on these new identifiers.

## Code 2
##### One-hot encode the node features
# Split moa and convert into indicator variables:
moa = drug_df['moa'].str.get_dummies('|')
# Use moa as drug input features:
drug_feat = torch.from_numpy(moa.values).to(torch.float)

# Split disease_categories and convert into indicator variables:
disease_categories = disease_df['categories'].str.get_dummies('|')
# Use disease_categories as drug input features:
disease_feat = torch.from_numpy(disease_categories.values).to(torch.float)

##### re-index the nodes incrementally
# Create a mapping from unique user indices to range [0, disease_nodes):
unique_disease_id = treatment_df['from'].unique()
unique_disease_id = pd.DataFrame(data={
    'diseaseId': disease_df.index,
    'mappedID': pd.RangeIndex(len(disease_df)),
})

# Create a mapping from unique movie indices to range [0, drug_nodes):
unique_drug_id = treatment_df['to'].unique()
unique_drug_id = pd.DataFrame(data={
    'drugId': drug_df.index,
    'mappedID': pd.RangeIndex(len(drug_df)),
})

##### reformat the edge with the new node indices
# Perform merge to obtain the edges from drugs and diseases:
treatment_disease_id = pd.merge(treatment_df['from'], unique_disease_id,
                            left_on='from', right_on='diseaseId', how='left')
treatment_disease_id = torch.from_numpy(treatment_disease_id['mappedID'].values)
treatment_drug_id = pd.merge(treatment_df['to'], unique_drug_id,
                            left_on='to', right_on='drugId', how='left')
treatment_drug_id = torch.from_numpy(treatment_drug_id['mappedID'].values)

# With this, we are ready to construct our `edge_index` in COO format
# following PyG semantics:
edge_index_disease_to_drug = torch.stack([treatment_disease_id, treatment_drug_id], dim=0)
print (edge_index_disease_to_drug.size())

These matrices were then packaged as a PyG HeteroData object. It is noteworthy that the x attribute holds the node features (Code 3).

## Code 3
##### Pacakge the data into a HeteroData object

from torch_geometric.data import HeteroData
import torch_geometric.transforms as T

data = HeteroData()

# Save node indices:
data["disease"].node_id = torch.arange(len(unique_disease_id))
data["drug"].node_id = torch.arange(len(unique_drug_id))

# Add the node features and edge indices:
data["disease"].x = disease_feat
data["drug"].x = drug_feat
data["disease", "may_be_treated_by", "drug"].edge_index = edge_index_disease_to_drug

# We also need to make sure to add the reverse edges from drug to disease
# in order to let a GNN be able to pass messages in both directions.
# We can leverage the `T.ToUndirected()` transform for this from PyG:
data = T.ToUndirected()(data)

Afterward, I employed an 80:10:10 data split, allocating 80% of the links for training the model, 10% for validation during training, and the remaining 10% for final testing after training is complete.

## Code 4

# For this, we first split the set of edges into
# training (80%), validation (10%), and testing edges (10%).
# Across the training edges, we use 70% of edges for message passing,
# and 30% of edges for supervision.
# We further want to generate fixed negative edges for evaluation with a ratio of 2:1.
# Negative edges during training will be generated on-the-fly.
# We can leverage the `RandomLinkSplit()` transform for this from PyG:
transform = T.RandomLinkSplit(
    num_val=0.1,
    num_test=0.1,
    disjoint_train_ratio=0.3,
    neg_sampling_ratio=2.0,
    add_negative_train_samples=False,
    edge_types=('disease', 'may_be_treated_by', 'drug'),
    rev_edge_types=('drug', 'rev_may_be_treated_by', 'disease'),
)

train_data, val_data, test_data = transform(data)

Both disjoint_train_ratio=0.3 and neg_sampling_ratio=2.0 are unique to GNN. The former indicated a 70/30 split of the graph edges. 70% were used for message passing and 30% were reserved for supervision. In other words, messages were only allowed to pass among those 70% of edges, but not among the 30%. Those 30% were used as learning targets. The negative sampling ratio dictates that for each existing edge, PyG created two non-existing edges as negative targets.

## Code 5
# In the first hop, we sample at most 20 neighbors.
# In the second hop, we sample at most 10 neighbors.
# In addition, during training, we want to sample negative edges on-the-fly with
# a ratio of 2:1.
# We can make use of the `loader.LinkNeighborLoader` from PyG:
from torch_geometric.loader import LinkNeighborLoader

# Define seed edges:
edge_label_index = train_data['disease', 'may_be_treated_by', 'drug'].edge_label_index
edge_label = train_data['disease', 'may_be_treated_by', 'drug'].edge_label

train_loader = LinkNeighborLoader(
    data=train_data,
    num_neighbors=[20, 10],
    neg_sampling_ratio=2.0,
    edge_label_index=(('disease', 'may_be_treated_by', 'drug'), edge_label_index),
    edge_label=edge_label,
    batch_size=128,
    shuffle=True,
)

In the next code block (Code 5), the edge_label_index variable holds the supervision edges (30%) while edge_label holds the message passing edges (70%). Similar to other neural networks, GNN are also trained in batches. PyG simplifies batch handling through its LinkNeighborLoader class. In Code 5, we set the batch size to 128. The num_neighbors parameter merits some explanation. A core strength of GNNs is their ability to aggregate information between neighboring nodes (message passing). However, considering messages from nodes several hops away can lead to a significant amount of computation. To address this, we can limit the number of neighbors considered during message passing. This is achieved by setting the num_neighbors parameter. In our example, a value of [20, 10] indicates that at most 20 neighbors will be sampled in the first message passing step (1-hop), and at most 10 neighbors will be sampled in the second step (2-hop). This helps control the computational cost.

The model is defined in Code 6.

## Code 6
from torch_geometric.nn import SAGEConv, to_hetero
import torch.nn.functional as F

class GNN(torch.nn.Module):
    def __init__(self, hidden_channels):
        super().__init__()

        self.conv1 = SAGEConv(hidden_channels, hidden_channels)
        self.conv2 = SAGEConv(hidden_channels, hidden_channels)

    def forward(self, x: Tensor, edge_index: Tensor) -> Tensor:
        x = F.relu(self.conv1(x, edge_index))
        x = self.conv2(x, edge_index)
        return x

# Our final classifier applies the dot-product between source and destination
# node embeddings to derive edge-level predictions:
class Classifier(torch.nn.Module):
    def forward(self, x_disease: Tensor, x_drug: Tensor, edge_label_index: Tensor) -> Tensor:
        # Convert node embeddings to edge-level representations:
        edge_feat_disease = x_disease[edge_label_index[0]]
        edge_feat_drug = x_drug[edge_label_index[1]]

        # Apply dot-product to get a prediction per supervision edge:
        return (edge_feat_disease * edge_feat_drug).sum(dim=-1)


class Model(torch.nn.Module):
    def __init__(self, hidden_channels):
        super().__init__()
        self.disease_lin = torch.nn.Linear(data["disease"].num_features, hidden_channels)
        self.drug_lin = torch.nn.Linear(data["drug"].num_features, hidden_channels)
        self.disease_emb = torch.nn.Embedding(data["disease"].num_nodes, hidden_channels)
        self.drug_emb = torch.nn.Embedding(data["drug"].num_nodes, hidden_channels)

        # Instantiate homogeneous GNN:
        self.gnn = GNN(hidden_channels)

        # Convert GNN model into a heterogeneous variant:
        self.gnn = to_hetero(self.gnn, metadata=data.metadata())

        self.classifier = Classifier()

    def forward(self, data: HeteroData) -> Tensor:
        x_dict = {
          "disease": self.disease_lin(data["disease"].x) + self.disease_emb(data["disease"].node_id),
          "drug": self.drug_lin(data["drug"].x) + self.drug_emb(data["drug"].node_id),
        }

        # `x_dict` holds feature matrices of all node types
        # `edge_index_dict` holds all edge indices of all edge types
        x_dict = self.gnn(x_dict, data.edge_index_dict)
        pred = self.classifier(
            x_dict["disease"],
            x_dict["drug"],
            data['disease', 'may_be_treated_by', 'drug'].edge_label_index,
        )

        return pred


model = Model(hidden_channels=64)

The Model class, through its forward function, orchestrates how date flows within the network. First, both nodes and their associated features are transformed: nodes are embedded in a lower-dimensional space, while features are processed by a linear layer. These transformed representations are then combined and fed into two stacked SAGEConv layers. These layers perform message passing, allowing the network to learn from the first two hops of neighboring nodes (70% of the edges). Finally, a classifier layer takes the dot product of the learned embeddings for drugs and diseases and uses the output logits to predict the supervision edges (30% of the edges).

Training in PyG follows the standard PyTorch training loop structure. The binary cross entropy is calculated as the loss (Code 7).

## Code 7
import tqdm
import torch.nn.functional as F

device = torch.device('cuda' if torch.cuda.is_available() else 'cpu')
print(f"Device: '{device}'")

model = model.to(device)
optimizer = torch.optim.Adam(model.parameters(), lr=0.001)

for epoch in range(1, 20):
    total_loss = total_examples = 0
    for sampled_data in tqdm.tqdm(train_loader):
        optimizer.zero_grad()

        sampled_data.to(device)
        pred = model(sampled_data)

        ground_truth = sampled_data['disease', 'may_be_treated_by', 'drug'].edge_label
        loss = F.binary_cross_entropy_with_logits(pred, ground_truth)

        loss.backward()
        optimizer.step()
        total_loss += float(loss) * pred.numel()
        total_examples += pred.numel()
    print(f"Epoch: {epoch:03d}, Loss: {total_loss / total_examples:.4f}")

The model was trained after 20 epochs. It was then validated and tested. While only the validation loop is shown in Code 8, swapping the validation data for the test data within the code effectively creates the test loop.

## Code 8: the validation loop. If we change the data to the test set, 
## we got ourselves the test loop

from sklearn.metrics import roc_auc_score

# change these two lines to test_data
edge_label_index = val_data['disease', 'may_be_treated_by', 'drug'].edge_label_index
edge_label = val_data['disease', 'may_be_treated_by', 'drug'].edge_label

val_loader = LinkNeighborLoader(
# change this line to test_data
    data=val_data,
    num_neighbors=[20, 10],
    edge_label_index=(('disease', 'may_be_treated_by', 'drug'), edge_label_index),
    edge_label=edge_label,
    batch_size=3 * 128,
    shuffle=False,
)

preds = []
ground_truths = []
for sampled_data in tqdm.tqdm(val_loader):
    with torch.no_grad():
        sampled_data.to(device)
        preds.append(model(sampled_data))
        ground_truths.append(sampled_data['disease', 'may_be_treated_by', 'drug'].edge_label)

pred = torch.cat(preds, dim=0).cpu().numpy()
ground_truth = torch.cat(ground_truths, dim=0).cpu().numpy()
auc = roc_auc_score(ground_truth, pred)
print()
print(f"Validation AUC: {auc:.4f}")

## Validation AUC: 0.8826
## Test AUC: 0.9029

The validation and test loops returned ROC AUC scores of 88% and 90%, respectively (Figure 7). Finally, we could convert the logits from the classifier to probabilities like this.

## Code 9
def logit_to_proba(logit):
    return 1/(1+ math.exp(-logit))

With this conversion, we could see how confident the model was about each prediction.

3. Examining some novel drug-disease predictions

The validation and test scores indicated decent model performances. Interestingly, the model made some novel drug-disease connections during my multiple runs. Here are some of them (Table 1).

The first pair Pneumonia, Bacterial-cefoxitin sodium received a high prediction score. Cefoxitin sodium is a beta-lactam antibiotic with bactericidal activity. So this new link seems reasonable. In fact, medlineplus.gov indeed stated that cefoxitin injection is used to treat infections caused by bacteria, including pneumonia and other lower respiratory tract (lung) infections.

There is also evidence supporting the Sinusitis-chloramphenicol prediction. Based on their own clinical experience and a pilot study, Nielsen et al. stated in 2013 that chloramphenicol eye drops may have a favorable effect on many patients troubled by acute maxillary sinusitis.

In contrast, Listeriosis-amphotericin B liposomal can be a harmful combination. Geginat et al. observed that the amphotericin B weakened the acquired immune protection against Listeria in mice. Specifically, the drug inhibited the CD8 T cell function. Regarding the fourth pair, liothyronine is used to add thyroid hormone to the body for patients with thyroid problems. However, there’s no evidence to suggest that it’s effective in managing muscle spasticity.

Conclusion

Computer-aided and data-driven drug developments have seen a surge thanks to machine learning and big data. It allows researchers to analyze massive datasets on molecules and their properties. In this article, I described my experiment with graph neural networks to predict novel drug indications. The GNN was implemented in PyG and achieved good validation and test scores. Nevertheless, users must examine its link prediction critically. As reported above, some of the predicted drug-disease connections seemed promising, while the others should be avoided.

PyG allows us to customize their own GNN. However, this requires writing low-level code that might prove difficult even for seasoned programmers. However, the current PyG pipeline requires a bipartite graph format, forcing us to squeeze information like Mechanism of Action (MOA), physiological effects, and drug relationships into single node properties. This data engineering leads to loss of information and likely sacrifices valuable insights, because the compressed format might obscure the intricate connections among drugs. In comparison, Neo4j’s GDS could be more friendly for GNN newcomers.

There are many ways to extend the current study. For starters, we could try to use “PE” and “parents” as drug properties. Or we can combine all three of them. In any case, some dimension reductions will be needed, because “PE” has 509 and “parents” has 404 unique values. In addition, we can get more drug-disease pairs from UMLS. We can also try other architectures such as graph attention networks (GAT) on the same task. Last but not least, we could compare the performance of GNN with other machine learning methods to understand its strengths and weaknesses.
